8 Gang of Four (GoF) Design Patterns

Every pattern in Velto solves a concrete architectural challenge in real-world ride sharing. Click "Execute Live Pattern Test" on any card to run the real backend subsystem and inspect its execution live in your viva presentation!

Pattern 1: Creational com.velto.pattern.factory
Factory Method Pattern

Domain Problem: Dynamic polymorphic user creation with role-specific invariants (Passengers require payment preferences; Drivers require vehicle details and license; Admins require audit rights).

Implementation: UserFactory interface with UserFactoryImpl instantiating Passenger, Driver, or Admin based on role.

Pattern 2: Behavioral com.velto.pattern.strategy
Strategy Pattern

Domain Problem: Real-time dynamic pricing calculation varies dynamically based on rush hours, weather, or carpooling incentives without modifying calling code.

Implementation: PricingStrategy with StandardPricingStrategy (1.0x), PeakPricingStrategy (1.5x surge), and SharedRidePricingStrategy (0.8x discount), coordinated via PricingContext.

Pattern 3: Creational com.velto.pattern.builder
Builder Pattern

Domain Problem: Construction of complex Ride documents with numerous mandatory and optional attributes avoiding telescoping constructors.

Implementation: Fluent nested static Ride.Builder with mandatory parameter validation ensuring rides cannot be built with missing driver info or zero seats.

Pattern 4: Structural com.velto.pattern.facade
Facade Pattern

Domain Problem: Ride booking touches 6 separate subsystems: User verification, Ride status validation, Seat availability check, Strategy pricing, Payment processing, and Persistence.

Implementation: RideBookingFacade.bookRide(...) shields clients from internal complexity by executing all 6 steps atomically behind a single call.

Pattern 5: Behavioral com.velto.pattern.state
State Pattern

Domain Problem: Ride lifecycles follow a strict state machine (REQUESTED → CONFIRMED → DRIVER_ASSIGNED → DRIVER_ARRIVING → IN_PROGRESS → COMPLETED). Illegal transitions must be strictly blocked.

Implementation: RideState interface implemented by 7 concrete classes and coordinated by RideContext.

Pattern 6: Behavioral com.velto.pattern.observer
Observer Pattern

Domain Problem: When a ride state changes, passengers, drivers, and administrators must receive real-time notifications without tightly coupling the status machine to notification logic.

Implementation: RideEventSubject notifies PassengerNotificationObserver, DriverNotificationObserver, and AdminNotificationObserver.

Pattern 7: Structural com.velto.pattern.adapter
Adapter Pattern

Domain Problem: Third-party payment gateways (UPI, Stripe/Card, Cash Counters) have incompatible method signatures, parameters, and return types.

Implementation: PaymentProcessor target interface with UpiPaymentAdapter, CardPaymentAdapter, and MockPaymentAdapter resolved dynamically via PaymentProcessorFactory.

Pattern 8: Creational com.velto.pattern.singleton
Singleton Pattern

Domain Problem: Application-wide runtime configurations (surge multiplier, base fare, maintenance mode) must be thread-safe and universally identical across all concurrent threads.

Implementation: AppConfigSingleton using Double-Checked Locking (DCL) with volatile, reflection prevention, cloning defense, and serialization readResolve.
